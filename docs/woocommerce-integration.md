# Как позже подключить настоящее оформление WooCommerce

Документ описывает **план**, а не реализованную интеграцию. Ничего из описанного
ниже в прототипе не подключено и не проверено на живом магазине. Совместимость
можно подтвердить только после доступа к тестовой копии сайта.

## Что уже подготовлено в коде

Данные каталога, корзина и оформление разделены, чтобы интеграция не потребовала
переписывать интерфейс:

| Слой | Где лежит | Что заменяется при интеграции |
| --- | --- | --- |
| Снимок каталога | `src/data/catalog.json`, сборщик `tools/fetch-catalog.mjs` | Источник данных: файл → запрос к API магазина |
| Типы каталога | `src/lib/types.ts` | Не меняется, если поля сохранены |
| Сопоставление и разбор | `src/lib/match.ts`, `parseOrder.ts`, `importSheet.ts` | Не меняется |
| Корзина | `src/state/useCart.ts`, `src/lib/storage.ts`, `totals.ts` | Локальное хранение → корзина магазина |
| Оформление | `src/components/Checkout.tsx` | Демо-экран → переход в оформление магазина |

Позиции корзины хранятся по `source_id` — это `id` товара WooCommerce. Именно он
нужен для любого из вариантов ниже.

## Вариант A. Передача корзины ссылкой (самый дешёвый)

WooCommerce понимает параметр `?add-to-cart=<id>&quantity=<n>` для одного товара.
Для нескольких позиций нужен небольшой плагин или сниппет в `functions.php`,
который читает список из параметра и наполняет корзину, после чего перенаправляет
на `/checkout/`.

- Плюсы: интерфейс остаётся статическим, оплата и заказ целиком на стороне магазина.
- Минусы: нужен код на стороне WordPress; длина URL ограничена.
- Что проверить: сохраняются ли позиции при переходе, как ведёт себя корзина,
  если товар кончился между сборкой и переходом.

## Вариант B. Store API (без плагинов, но с ограничениями)

У магазина уже открыт публичный `POST /wp-json/wc/store/v1/cart/add-item`.
Он работает с корзиной посетителя и требует заголовок `Nonce`, который выдаётся
при `GET /wp-json/wc/store/v1/cart`.

- Плюсы: не нужен серверный код, корзина настоящая.
- Минусы: запросы идут с чужого домена — потребуется настройка CORS или размещение
  прототипа на том же домене; поведение nonce и cookies надо проверять отдельно.
- Что проверить: CORS, срок жизни nonce, корректность ответа при отсутствии товара.

## Вариант C. Прототип как тема или страница внутри WordPress

Собранная статика встраивается в шаблон страницы магазина, корзина используется
штатная.

- Плюсы: один домен, никаких CORS и nonce-проблем, весь оформительский поток родной.
- Минусы: нужен доступ к теме и деплой внутрь WordPress.

## Рекомендация

Начать с варианта C, если владелец готов дать доступ к тестовой копии: он даёт
наименьший риск и настоящий заказ WooCommerce без промежуточных слоёв. Вариант A —
запасной, если доступ к теме получить нельзя.

## Что нужно получить от владельца перед интеграцией

1. Тестовая копия сайта (staging) — на боевом магазине такие вещи не проверяют.
2. Решение по варианту интеграции (A / B / C).
3. Доступ к теме или возможность установить плагин — для A и C.
4. Подтверждение, какие поля обязательны в оформлении и какие способы доставки есть.
5. Правила по весу: у части товаров фасовка не опубликована — нужно решить,
   заполнять её в карточках или считать вес только по известным позициям.
6. Ответ, нужны ли оптовые цены и остатки: сейчас магазин их не публикует,
   поэтому прототип их не показывает.
7. Разрешение на использование фотографий товаров на отдельном домене.

## Чего делать нельзя до проверки

- Обещать, что заказ из прототипа попадёт в WooCommerce: это не проверено.
- Переносить снимок каталога в продажу как источник истины — цены и наличие
  в нём зафиксированы на дату снимка.
